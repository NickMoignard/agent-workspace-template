# Agent Workspace Template

The shared language for this template: what a workspace is, what it groups, and
how it references the projects worked on inside it. This is a glossary, not a
spec. This is the workspace's own context; `CONTEXT-MAP.md` indexes it alongside
one context per referenced project.

## Language

**Agent Workspace** (or **Workspace**):
A parent directory that bundles agent instructions, skills, an issue tracker,
and editor config, and gathers one or more Projects to be worked on together. A
Workspace is independent of the Projects it references: it does not track their
history or pin their commits.
_Avoid_: repo (a Workspace is not one of the code repos), monorepo.

**Project**:
A source-code repository worked on inside a Workspace. A Project's canonical
clone lives outside the Workspace, in the Git source dir; the Workspace only
references it. One Project may be referenced by many Workspaces at once.
_Avoid_: submodule (the retired mechanism), package, module.

**Git source dir**:
The single machine-level directory where Project clones physically live, one
subdirectory per Project. Its location is the environment variable
**`AGENTS_GIT_SRC_DIR`** (default `~/agents/git_repos`). Because clones are
shared here, editing a Project in one Workspace is reflected in every Workspace
that references it.
_Avoid_: cache, vendor dir.

**Projects directory**:
The `projects/` folder inside a Workspace. It holds one **symlink** per
referenced Project, `projects/<basename> -> $AGENTS_GIT_SRC_DIR/<basename>`. The
symlinks are git-ignored (machine-specific absolute paths); only the Manifest
and a committed `projects/README.md` persist. The VS Code folder list is
regenerated by scanning this directory.
_Avoid_: submodules dir, packages dir.

**Manifest**:
The committed file in a Workspace that declares which Projects it references, as
a list of clone URLs. Clones always follow each remote's default branch; the
Manifest never names a branch or pins a commit. The symlink name defaults to the
repo basename. It is a **YAML** file, `projects.yaml`, parsed with `yq`, whose
one key `projects:` is a flat list of clone-URL strings.
_Avoid_: lockfile (it does not pin versions), .gitmodules.

**Bootstrapping** (the **create-agent-workspace** skill):
Creating a new Workspace by scaffolding this template's contents into an empty
directory. Done by the `create-agent-workspace` skill, installed standalone via
the skills.sh CLI (`npx skills`), so an agent can run it in any empty dir. It
runs a mechanical file-copy (the bootstrap script), then an interactive
setup conversation (rewrite the README, configure `projects.yaml`, choose
default skills). The skill lives in its own standalone repo
(`create-agent-workspace`); this template repo is the scaffold source it fetches.
The new Workspace does not inherit the template's git history.
_Avoid_: fork, clone (the new Workspace is neither).

## Flagged ambiguities

- **"add a project"** now means *record it in the Manifest, clone it into the
  Git source dir if absent, and symlink it into `projects/`* — no longer
  `git submodule add`.

## Example dialogue

> **Dev:** Is `yamlx` part of this workspace?
> **Expert:** It's a Project the workspace *references*. The clone lives in the
> Git source dir (`$AGENTS_GIT_SRC_DIR/yamlx`); `projects/yamlx` is just a
> symlink to it.
> **Dev:** So if I open a second workspace that also lists `yamlx`?
> **Expert:** Same clone. Both `projects/yamlx` symlinks point at the one copy
> in the Git source dir. The workspaces stay independent of `yamlx`'s history;
> neither pins its commit.
> **Dev:** Where's the list of what to clone?
> **Expert:** The Manifest, committed in the workspace. It says *which* Projects
> and *from where*, not *at which commit*.
