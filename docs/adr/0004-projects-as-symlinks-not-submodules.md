# 4. Reference projects as symlinks to shared clones, not git submodules

Date: 2026-09-11

## Status

Accepted

## Context

The template originally added each project as a **git submodule**. That couples
the workspace to the projects it is used on: the parent repo pins each
submodule's exact commit, `git status` churns as project work happens, and a
project referenced by two workspaces is cloned (and version-pinned) twice,
independently. A workspace is meant to be a *lens* onto some projects, not a
tracker of their history. Submodules make the workspace and its projects move as
one unit, which is the opposite of what we want.

We also gained `yq`/`jq` as hard requirements (installed via Homebrew), so the
mechanical layer can parse structured config without a bespoke parser.

## Decision

Projects are **referenced by symlink**, declared in a committed manifest, and
cloned once per machine into a shared source directory:

- **Git source dir.** Clones live in `$AGENTS_GIT_SRC_DIR` (default
  `~/agents/git_repos`), one dir per repo. The same clone is shared by every
  workspace that references it. Editing a project in one workspace is seen by
  all of them.
- **Manifest.** `projects.yaml` (committed) has one key, `projects:`, a flat
  list of clone-URL strings. It declares *which* projects, never a branch or a
  commit. Clones follow each remote's default branch; reproducibility, when
  wanted, is the user's own git concern inside the clone. Parsed with `yq`.
- **Projects directory.** `projects/` holds one symlink per project,
  `projects/<basename> -> $AGENTS_GIT_SRC_DIR/<basename>`. The symlinks and
  clones are git-ignored (they are machine-specific absolute paths); only
  `projects.yaml` and a `projects/README.md` are committed.
- **Layer split (per ADR 0001).** A new `/setup-projects` **skill** owns the
  environment-adaptive parts: ensure `AGENTS_GIT_SRC_DIR` is set (written to the
  shell rc file, marker-guarded, like `/setup-homebrew` and `/setup-asdf`),
  create the directory, then invoke the mechanical sync. A new
  `scripts/sync-projects.sh` does the deterministic work: read `projects.yaml`,
  `git clone` any missing repo into the source dir, and (re)create the symlinks.
- **VS Code folders** are regenerated by scanning `projects/` for symlinks
  (reflecting on-disk reality), not by reading `.gitmodules` or the manifest.
- **Renamed operations.** `add-submodule` -> `add-project` (append to
  `projects.yaml`, clone, link), `update-submodules` -> `update-projects`
  (`git pull` each clone). `.gitmodules` and `git.detectSubmodules` are removed.

## Consequences

- The workspace no longer pins project commits and no longer churns when project
  code changes; the workspace repo tracks only its own config.
- One clone serves many workspaces, so disk and fetch cost drop and edits are
  shared. The trade-off: a workspace cannot guarantee a specific project commit
  the way a submodule did. That is accepted, and is the whole point.
- Symlinks and clones cannot be committed (absolute, per-machine paths), so a
  fresh clone is not usable until `/setup-projects` has run. `make setup` runs
  the mechanical sync when `AGENTS_GIT_SRC_DIR` is set and otherwise points at
  `/setup-projects`.
- Onboarding gains a step: `/setup-homebrew` -> `/setup-asdf` -> `/setup-beads`
  -> `/setup-projects` -> `make setup`.
- Two projects sharing a repo basename collide on the symlink name; treated as a
  documented edge case (rename at the source) rather than schema complexity.
